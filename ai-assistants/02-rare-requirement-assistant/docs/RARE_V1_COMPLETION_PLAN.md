# RARE v1 Completion Plan

## Purpose and scope

This checklist maps the original product roadmap in `RARE_AI_Assistant— Project Planning full.docx` to implementation work. The document contains multiple drafts and a second delivery-phase numbering track; this file uses the original product roadmap phases 0–15 as the capability checklist. Delivery Phase 15 (hardening, documentation, release) is the final release gate. Phases 16–20 are not part of the approved original roadmap.

The ReqTestAgent-inspired workflow is included where it fits the original scope: domain-neutral requirement ambiguity review in Phase 6, RAG evidence retrieval in Phase 7, generated executable automation in Phase 8 / delivery Phase 13, and reference execution plus mutation checks in Phase 14 when a runnable target and trustworthy oracle are available. The user has also requested a delivery sequence numbered 16–20 to track implementation of these capabilities; those labels are work packages, not claims that the original v1 phases are complete.

## Working rules

- Do not add industry-specific assumptions, sample data, or business rules to shared logic. Derive behavior from the uploaded documents, configurable schemas, or explicit user decisions.
- Treat generated results as proposals. Preserve source documents and prior test-case versions; retire/archive only through a visible, confirmed workflow.
- Validate changes in an isolated workspace first. Do not use the live JSON repositories as scratch data or overwrite them during tests.
- For each workstream, define acceptance checks, implement one small increment, run focused tests, run integration/regression checks, then update the code-section record and technical guide with the exact changes.
- If a BRD has no runnable application/reference implementation, execution-based verification is `NOT AVAILABLE` for that project. It must not be reported as a pass. Mutation testing is conditional on a functioning execution adapter.

## Current baseline

- The project is an existing Streamlit application with PDF/DOCX/image intake, OCR integration, LLM-driven test-case generation, JSON requirement/test-case/traceability repositories, change detection, traceability, coverage, quality checks, and Excel export.
- The latest full automated suite result is 94 passed, 44 warnings (2026-11-14). This is evidence only for the tests that exist; it does not establish full product acceptance. A user-run BRD workflow now generated and stored a suite in an isolated project, but the reported requirement coverage was 45.45% and remains a quality gap.
- Google Drive, RAG/vector retrieval, requirement ambiguity analysis, executable-test generation, an application-under-test runner, and mutation testing are not implemented in the current main workflow. Phase 1 now has a project selector and project-scoped JSON repository paths for newly created workspaces; the existing shared workspace remains the default.
- The repository contains existing live JSON data. Migration or storage replacement must be additive, backed up, and verified against a copy before any live-data cutover.

## Recommended implementation order

The plan preserves the original dependency order while allowing isolated code changes to be built and checked before they reach the main UI:

1. **Phase 0 — Lock contracts and safety baseline.** Inventory source files and data, define project/document/requirement/test-case/source identifiers, and record migration/rollback acceptance. Do not change live repository contents.
2. **Phase 1 — Project workspace and data isolation.** A project selector and project-scoped requirement/test-case/traceability JSON paths are integrated. Next, add document ownership/version records, then test migration and rollback on copied repositories before any live cutover.
3. **Phases 2–4 — Document lifecycle and intelligence.** Add immutable document versions and provenance; complete supported-format and extraction behavior, including large/scanned files.
4. **Phases 5–7 — Requirement intelligence, validation, and RAG.** Improve generic structured extraction; add evidence-based ambiguity/consistency findings; then add retrieval and citations.
5. **Phases 8–10 — Test design and change lifecycle.** Improve generated case reliability, connect existing tests to requirements, and provide a user-confirmed archive/retire action that preserves prior versions.
6. **Phases 11–13 — Traceability, project state, and reports.** Ensure records remain linked across versions and export the planned artifacts.
7. **Phase 14 — Product evaluation.** Add repeatable quality datasets and metrics. Add canonical execution/mutation only for targets with an explicit executable adapter and trusted expected behavior.
8. **Phase 15 — Release gate.** Complete security, dependency, performance, UI, logging, documentation, demo, regression, and release-candidate checks.

## Not included in original v1 unless separately approved

Additional phases numbered 16–20, broad Jira synchronization, cross-project knowledge sharing, and enterprise-scale deployment features are not automatically part of the original v1. They can be proposed for a later release after the original acceptance checklist is closed. Google Drive, by contrast, is explicitly in the original product roadmap and remains a planned v1 capability.
